# Agent 工作流

1. 沟通：读取项目入口与相关模块设计，澄清目标、边界、验收标准；只读讨论不修改代码。
2. 范围确认：确认当前范围版本，识别依赖与受影响模块。
3. PRD：提出完整方案、用户流程、异常场景和模块完成后的设计；由用户确认具体版本。
4. 实施：在独立工作区按确认版本实现，维护 IMPLEMENTATION.md 并执行授权范围内的必要验证。
5. 迭代：设计有变化时同步 PRD.md 与 modules/<模块 ID>.md，说明差异；系统读回为新 PRD，用户重新确认后继续对应实施。
6. 回归：逐条核对验收标准，在 VERIFICATION.md 记录真实结果和未覆盖项；平台检查与人工验收分别保留。
7. 收束：向用户呈现改动、证据和待决定项；用户验收后固化 PRD，之后的设计变更创建关联子需求。
8. 集成：在隔离候选中同步主线、解冲突、重新验证；产品语义取舍交给用户，最终合入需确认。

优先读取根 AGENTS.md、相关路径下的 AGENTS.md 与本轮 CONTEXT.md。只读取当前需求相关模块与依赖，不无差别加载所有历史。跨需求交接保留范围 ID、PRD ID、模块基线、交付和真实验证信息。

新建或已导入的需求以界面展示路径的 Markdown 编辑正文，JSON 仅作只读依据。未导入旧需求仍兼容 JSON / Markdown 合并；两处改动冲突时先合并，不任意覆盖。文档目录可在项目设置中配置，已有绑定不自动移动。CONTEXT.md 与 baselines/ 是系统快照，不修改确认 ID、验收状态或基线事实。

## 连续推进与复审

- 讨论阶段可提交一个 `qingzhou-design` JSON 代码块，字段为 schemaVersion、itemId、scopeId、expectedPrdId、content、reason、moduleChanges、questions。平台按本轮依据提取为提案；用户采用后仍需保存和确认。
- 新 PRD 确认时绑定代码 commit 和该代码包含的模块版本。已验收未合入设计单独保留，不能自行作为其他主线需求的现状。读取 CONTEXT.md 中的 PRD 绑定代码以及确切模块基线。
- “实施并验证”是用户单独授权的自动轮次：可以封存本需求全部改动、执行项目检查并按 0–3 轮上限修复。设计变化、配置变化、失败或中断时暂停，不自行确认新设计、验收或合入。停止自动推进保留当前运行轮次；停止本轮执行仍使用原停止入口。
- 模块文档同步到稳定的 `docs/modules/<模块 ID>.md`，随代码交付。编辑设计应先改需求模块提案，再同步到正式文档；不以手改仓库文档绕过 PRD 确认。
- 集成修复不得改写本需求或主线已有的固化 PRD 与执行快照。组合检查后必须针对确切候选进行行为复审。候选或验证改变后重新复审；若改变产品设计，取消候选并创建关联子需求。
- 同模块并行合并可维护组合后的模块文档，复审后随 Git 合入发布独立集成设计版本；来源 PRD 保持固化，版本通过集成记录关联双方代码与原设计。
