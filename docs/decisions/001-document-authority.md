# ADR-001：文档编辑与状态权责

状态：本轮已实施，待用户验收。关联 [项目标准需求](../requirements/project-standards/PRD.md)。

## 背景

已有需求设计 JSON 与平台版本、交付和验收绑定。Agent 需要可读的产品与模块文档、明确的实施依据和可编辑提案；串行与并行需求都需要保留确切版本。目录标准也需要兼容既有仓库说明和代码框架。

## 决定

- 保留已有 JSON 路径和依据 ID，增加 Markdown 编辑入口。相对于所绑定的 PRD 分别判断修改；两处不同修改时要求合并，再由用户确认新 PRD。
- 将当前需求的可编辑提案与只读基线分开。每个需求拥有稳定目录，模块快照按模块和版本命名，减少并行需求争用共享文件。
- 平台保持范围确认、PRD、检查、验收、固化与集成的权威事实。实施、验证 Markdown 记录实际过程和证据位置，不授予产品状态。
- 项目初始化先预览，新增缺失文件并保留已有规则。源码继续沿用原项目结构，历史 PRD 通过索引保留。
- Agent 提示只给读取顺序和本轮确切依据，详细上下文可在执行指令中展开，聊天正文保留用户目标。

## 取舍与影响

JSON 单入口便于验证，但对人和 Agent 阅读编辑不够直接。增加 Markdown 后需要处理双入口冲突；明确依据版本与拒绝静默覆盖，使这项成本可控。后续若收敛为一种编辑入口，仍需保留既有设计 JSON 和交付关联的兼容读取。

共享模块当前文件容易在并行需求中竞争。需求内提案和版本快照分别进入交付；模块当前确认设计通过平台发布与历史文档维护表达，代码合入单独记录。原项目未提交改动仍不复制到新工作区。

## 验证

覆盖初始化幂等与保留已有 AGENTS.md、路径边界、JSON / Markdown 修改合并、无共同依据的残留提案、上下文和版本标记保护、Git 快照、并行集成及界面流程。结果见 [本需求验证记录](../requirements/project-standards/VERIFICATION.md)。

## Markdown 单入口修订（已实施，待验收）

依据 [文档审阅 PRD v1](../requirements/document-review-simplification/PRD.md)，新建及显式导入后的文档以项目 Markdown 为正文入口。状态仅保存路径、hash 与生命周期关联；历史正文使用不可变 Markdown 快照，读取时校验 hash。保存成功须完成文件与状态持久化，恢复日志只回滚本次写入，不覆盖外部修改。

目录配置保存在清单的可选 `documentPaths`；默认 `docs/requirements`、`docs/modules`，已绑定文档不随配置移动。原 JSON 路径仍保留只读执行依据，未导入的旧需求继续兼容以上双入口合并规则，既有交付不改路径或确认事实。

原目录中的平台文档须同时匹配登记 hash 和候选内容才能受控合入；初始模块基线只有在原目录与候选分别准确匹配初始和确认提案时才允许前进。人工暂存、未知文件和外部修改均阻止覆盖。Git 衔接记录独立恢复意图，重启不自动合入。
