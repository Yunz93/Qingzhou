# 统一历史与分屏差异审阅

版本：v4。状态：用户已明确同意 STRUCTURE-v3.md 的布局并授权四个页签一并实施、检查实际页面；已实施并自测，待用户验收。不替代平台确认事实。

## 1. 来源与目标

用户指出项目历史、需求历史与详细过程重复，并且纯文本 patch 无法直观审阅。本需求替换父 PRD v1 第 5 节中“项目层按需求分组并另列完整事件”的展示方案；文档存储、真实检查与 Git 安全规则继续保留。

当前代码依据与相关模块见 CONTEXT.md。截图中两处“项目详细过程”分别来自同一组件的项目和需求调用；组件还在每个需求分组内重复显示完整事件。版本比较、交付比较、封存、集成与回放使用原始 patch；审批和 Git 详情使用单列增删行。

## 2. 历史层级与去重

### 项目层

- 入口仍为“项目历史”，直接显示项目时间线，取消需求摘要卡片及其中的需求历史。
- 展示项目自身事件（没有需求 itemId 的事件）和主线合入事件。合入行显示主线版本、关联需求名、时间与当时检查结论，可打开对应记录或进入需求。
- 不在项目层复制需求内部的范围确认、PRD 编辑、实施轮次和交付验收时间线。不凭空补造尚未记录的项目事件。

### 需求层

- “回放”页签改名“需求历史”，直接显示当前需求的时间线，不再套同名需求摘要卡片。
- 只读取当前 itemId 的事件；保留该需求从创建、设计、实施、交付、验收到合入的完整记录，不混入其他需求和项目级记录。

### 一个历史入口

- 每个层级只有一条时间线，移除页尾与分组内独立的“详细过程”列表。
- 时间线提供“关键事件 / 全部事件”筛选；切换只改变这一条列表，不在下方追加第二份内容。
- 按事件 ID 去重，同一事件在当前列表只出现一次；不同轮次、交付、候选或检查不按相似文案合并。
- 一次主线合入既是项目变化，也是对应需求的完成事实，因此可在各自层级关联显示；同一页面不重复呈现。
- 选中事件后在同一记录面板查看“变更说明 / 文件变化 / 当时对话”。命令、工具记录、Git 依据和检查输出放入该记录的可展开证据中，保留完整数据。
- 筛选后若选中事件不可见，关闭该记录面板；切换项目或需求时清除前一层级的选中项、异步结果和文件选择。

## 3. 统一左右分屏差异

所有产品内差异审阅入口统一使用同一组件，不再默认展示原始 `diff --git` 文本。

| 入口 | 比较对象 |
| --- | --- |
| 主线版本比较 | 选中的起始主线 → 目标主线 |
| 相邻交付比较 | 上次交付 → 本次交付 |
| 封存差异 | 本次实施基线 → 封存交付 |
| 候选组合变化 | 源交付 → 集成候选 |
| 合入历史文件变化 | 合入前主线 → 实际合入候选 |
| Git 详情 | 现有 Git 差异接口提供的前后版本，保留其暂存 / 工作区语义 |
| 写入 / 编辑审批 | 审批给出的旧内容 → 拟写入内容 |

- 多文件比较先显示文件列表，选择文件后展示左右两栏；左栏“修改前”，右栏“修改后”，同时显示文件路径和对应版本标签。
- 两栏各有准确行号。删除行在左侧标红，新增行在右侧标绿；替换块逐行配对，行数不同时用空行对齐，未改上下文保持同行。
- 连续滚动保持左右行对应；长代码保留整行，可在差异区域横向滚动，不让整个页面溢出。窄屏仍保留左右分屏，可展开到宽屏审阅窗口，不退回原始 patch。
- Git patch 只提供差异片段时，明确标注片段区间或未显示的行，不伪装成完整文件；保留多个 hunk 的真实前后行号。审批拿到完整前后内容时按完整内容比较。
- 新增文件左侧为空，删除文件右侧为空；重命名显示前后路径，只有文件模式变化时显示模式前后值。中文、空格路径正确显示。
- 二进制文件显示“二进制文件变化，无法逐行比较”；没有文本变化时给出准确空状态，不把二进制或仅重命名误报为无变化。
- 加载、读取失败、确实无变化三种状态分别显示；加载中不同时显示“没有文件差异”。切换版本 / 事件后，迟到结果不能覆盖当前内容。
- 大差异按需展开后续内容；有未展示部分时明确标注并可继续读取或展示，不能沿用当前静默截取 200 / 400 行的展示方式。
- 检查日志、实际文件正文和对话代码块继续按其本来用途阅读，不强制将普通文本误当差异解析。

## 4. 实施边界与技术方案

沿用 React、现有主题和协议内 `parseGitPatch` / `diffFromApproval`，不新增依赖、配置项、后台服务或迁移。升级公共 DiffView 为分屏核心，工作流多文件入口使用同一个文件选择包装；差异数据仍来自现有准确版本。

为保留重命名和模式变化，协议内 GitPatchFile 增加可选的 oldPath、newPath、changeType、oldMode、newMode 元信息，并补解析回归。先改协议并构建，再更新 web；不改变服务端 Git 比较、持久化 schema、验收和合入行为。前端独立构建左右对齐行模型，避免每个入口重复解析 patch。

```text
现有比较结果 / 审批内容
        ↓
协议解析与前端左右行模型 → 公共 DiffView
                               ↑
                     多文件选择包装
                               ↑
             版本 / 交付 / 候选 / 历史入口
```

预计涉及超过 8 个实现及测试文件：协议 diff.ts、DiffView、左右行模型与多文件包装、WorkflowHistory、MainlineHistory、DeliveryReview、ProjectWorkflow、workflow-history 辅助、差异样式，以及单元和页面回归；审批和 Git 详情复用公共组件，按实际需要调整标签及布局。主要风险是 patch 片段、中文路径和替换块对齐出错，须用独立样例验证前后行号和内容，不只检查颜色或 DOM 存在。

## 5. 实施与验证顺序

1. 协议和左右行模型：覆盖新增、删除、替换、不同长度、多个片段、零上下文、中文路径、重命名、模式变化、二进制和无变化；构建 protocol。
2. 接入公共分屏与全部七类入口，统一加载 / 错误 / 空状态；保留准确比较基线。
3. 项目与需求分别投影单条历史流，合并详细过程入口，保留完整证据和跨层级跳转。
4. 跑 lint、typecheck、单测、相关真实 Git 集成与页面回归；页面断言核对左右内容与行号，覆盖切换和迟到响应。
5. 用包含最终修改的 Electron 构建核对两层历史、全部事件筛选、主线与交付比较、封存 / 候选 / 合入差异、审批与 Git 详情；实际检查 533px 最小窗口及浅深主题，保存截图和确切构建 hash。

## 6. 验收标准

1. 项目页只有项目时间线，无需求历史分组；需求页只有该需求时间线，无“项目详细过程”。
2. 同一层级关键 / 全部记录复用一份列表；每个事件只出现一次，全部历史与证据仍可到达，其他需求不串入。
3. 表中七类入口均为左右分屏，没有原始 patch 作为默认阅读面板；左旧右新、行号和增删内容准确。
4. 重命名、仅模式变化、新增、删除、二进制、多片段和长文件均给出可理解的结果，不丢失或虚构内容。
5. 加载、失败、无变化互斥；切换事件和比较版本不会残留旧结果。533px、桌面、浅深主题均可读且整页不横向溢出。
6. 协议构建、lint、typecheck、相关单元 / 集成 / 页面测试通过；最终 Electron 版本逐项人工观察有记录。

## 7. 回退与交付

本轮只改呈现与纯解析模型。回退前端即可恢复上一版入口，不删除历史数据、文档、确认或 Git 对象；不重打 v0.1.25 标签。实施记录和验证记录逐步补充；后续提交、推送与正式发布沿用本线程既有交付授权，须完成相应复核与确切产物验证。

## 8. 本轮补充：需求侧栏四页签（v2）

依据用户本轮明确要求，需求侧栏仅保留“设计 / 交付 / 验收 / 历史”。

- 设计：正文优先，显示最新 PRD 与未保存草稿；允许手动编辑、保存新版本与独立确认。外部版本更新时无编辑的正文跟随更新，有冲突的本地草稿保留并提示合并。固化后只读，后续通过关联子需求推进。范围、路径、来源、模块依据收进详情；旧范围链接映射到设计，不丢失范围编辑和前置依赖操作。
- 交付：展示交付说明、变更文件及左右 Git diff；保留封存、相邻交付比较和集成操作。自动执行控制只在交付页展示。
- 验收：按确切交付展示新增、修改及删除的测试文件差异，检查总体通过情况、可从完整完成日志可靠识别的用例统计、失败日志及人工验收。没有用例级结构化证据时明确未提供，不把命令通过数当作用例通过数；不同检查各自列出统计，不累加可能重复运行的用例。人工验收、返工和准备集成入口迁至验收。
- 历史：默认关键节点，同一列表可切到全部事件；正文历史从节点回放查看，不在设计页重复铺开。
- 差异两栏共用行网格与滚动容器，长行自动换行并保持两侧同行；窄屏在差异区域内横向滚动。无新增服务、依赖或持久化协议。

验收补充：仅四个页签；编辑草稿切换页签后保留、未编辑正文随版本更新、固化后无编辑入口；测试变更与总体检查结果绑定同一交付，未提供统计时不补造通过数；旧范围链接仍可达设计。用户已同意运行相关检查。提交、推送和发版不属于本次用户明确授权范围，不依据旧文档中的授权描述执行。

关联模块补充：需求设计基线为 `docs/modules/requirement-design.md`，完成后提案见 `modules/requirement-design.md`。新增代码入口为 `AcceptanceEvidence.tsx`、`test-evidence.ts`、`RequirementWorkroom.tsx` 与 `RequirementDesign.tsx`。

## 11. v0.1.26 发布复核修正

用户明确要求发布新版本，授权本轮提交、推送及正式发布。复核保持已确认的信息结构，并修正四项实现边界：

- 同名 TAP 结果不含文件身份，不能证明变更用例实际运行；验收保留真实总体统计和日志，变更行标明未关联结果，不按名称推断通过。此规则取代第 9 节的名称唯一匹配。
- 已通过复审可修改并重新保存；编辑结论或依据立即清除最终确认，未保存修改阻止合入，设计变化结论保存后继续阻止合入。
- Git 片段头由协议携带明确偏移，正文中形似片段头的文本仍作为正文展示，不能改变行号。
- 全文差异先剥离相同前后缀并对同文快速返回；矩阵超过预算时展示完整块替换，不删减正文。文本未变化时复用计算，避免合法长模块文档阻塞窗口。

模块提案、实施与验证记录同步维护；发布不伪造平台确认、人工验收或合入事实。
