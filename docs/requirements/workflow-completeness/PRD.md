# Agent 工作流闭环补全

状态：按用户“扣分点修改”授权实施，待最终验收。

## 目标

补齐评审发现的五处衔接：集成修复复审、代码对应的模块基线、结构化设计提案、有限自动验证修复、仓库模块文档同步。

## 行为

1. 集成候选保留源交付的固化 PRD 和执行快照；候选检查通过后，用户针对确切候选记录“行为保持一致”或“设计发生变化”。后者阻止合入，使用关联子需求重新设计。修复、重新验证和候选变化使旧复审失效。
2. 新确认的 PRD 绑定代码 commit 及该代码实际包含的模块设计版本。已验收未合入设计继续展示，但不自动成为其他主线需求的实施基线。旧 PRD 保留原版本约束。
3. 模块拥有稳定的仓库文档路径。实施生成与提案一致的模块 Markdown，作为交付审阅和 Git 合入的一部分；不同需求同模块的设计合并也必须复审，合入后的模块版本与实际仓库内容对应。既有手工文档不静默覆盖。
4. 只读讨论可输出带需求、范围和 PRD 依据的结构化设计提案。系统提取并展示正文、模块变更和待确认问题；用户采用为草稿，再保存和确认，不授予 Agent 确认权限。
5. 用户可单独启动“实施并验证”，明确授权封存当前需求全部改动及最多 0–3 轮失败修复。通过后等待人工验收。范围、PRD、检查配置变化，设计同步冲突、停止、执行失败、次数耗尽或重启均暂停/中断，不自动验收、合入或重放。

## 验收

- 改动后的候选不能沿用旧复审；候选篡改固化 PRD 时拒绝合入。
- A 验收未合入不污染 B 的主线设计基线；串行和同模块并行保留真实版本来路。
- 模块文档与交付一起封存，合入内容可回读为对应代码版本的模块设计。
- 结构化提案不直接改变范围确认或 PRD 确认，过期提案不能覆盖新版本。
- 自动轮次真实运行检查，失败日志进入后续修复，严格遵守次数和暂停边界。
- 兼容历史数据；相关单元、真实 Git 集成和浏览器回归通过。
