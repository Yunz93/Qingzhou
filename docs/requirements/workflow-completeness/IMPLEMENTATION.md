# 实施记录

## 改前与改后

| 环节 | 改前 | 改后 |
| --- | --- | --- |
| 集成候选 | 沿用源交付验收，只有最终合入确认 | 额外保存候选 commit/tree/PRD 对应的行为复审；变化与篡改使复审失效 |
| 模块基线 | 总是采用最新验收模块版本 | 新 PRD 绑定实际代码及该代码包含的模块版本 |
| 模块文档 | 平台版本更新，仓库文档靠人工维护 | 稳定文档路径，实施生成、封存核对、Git 合入、实际正文回读为集成修订 |
| 设计提案 | 整段 Agent 回复作为草稿 | 提取有版本依据的结构化提案，逐项审阅并由用户采用、保存和确认 |
| 实施验证 | 用户分别封存、检查并启动修复 | 单独授权自动轮次，真实检查与限定次数修复，通过后等待人工验收 |

## 代码与边界

- 协议：design.ts、workflow.ts、client-commands.ts 新增可选持久化字段和显式用户操作，兼容旧数据。
- 服务：workflow-design.ts、workflow-module-docs.ts 与 workflow-service.ts 负责版本、文档、复审与调度，workflow-store.ts 在重启时中断自动轮次。
- 界面：设计面板展示提案及代码基线，模块页区分主线版本，集成面板保存复审，需求工作区提供明确授权的自动轮次。
- 既有人工源码文档保留；新模块和新 PRD 实施的历史模块使用独立的稳定 ID 路径。平台生成的模块文档需通过提案修改，避免与手工文档互相覆盖。
- 不自动验收、固化、合入、提交本仓库或推送远端。
- 自动轮次等待项目验证名额；等待和文件读取期间取消不会复活轮次。只读讨论的执行上下文与原始提案默认折叠，正文保留问题和待确认事项。
