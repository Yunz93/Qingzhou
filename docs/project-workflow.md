# 项目需求编排：使用与实施记录

本轮依据 [PRD](prd/project-work-orchestration.md) 实施。此前审查修复已单独提交为 `a122bf7`；产品改造保留为独立工作区改动。

## 使用流程

1. 在「工作」中创建或选择项目，打开「配置工作模式」，选择本地 Git 集成分支。默认并发为 1，可设为 2–16。非 Git 项目保留原对话与任务能力，不能启用隔离合入。
2. 添加项目检查：名称、实际命令、是否必需、超时及可选独占资源。命令会在独立工作区运行；依赖安装须包含在命令中。凭据使用已有环境变量，原目录的 `.env`、未跟踪文件和未提交改动不会复制。
3. 新建需求，填写说明和验收标准。单条开始，或选择多条批量开始；前置需求尚未合入时等待，独立需求按稳定排序继续执行。可暂停后续队列，或逐条停止活动轮次。
4. 进入需求工作区，在左侧连续对话中实施及补充要求。右侧「范围」编辑目标，「交付」处理验证与合入，「回放」查看历史。正常结束只表示本轮对话结束。在「交付」中，查看待封存文件、确认归属，再「封存所选改动并验证」。所有待封存改动都必须明确确认，避免混入来源不明的文件。
5. 系统保存不可变交付提交、代码树、文件差异、固定范围及本轮对话。按实际退出码保存检查日志。没有必需检查、检查中断、超时或必需检查失败时，交付不能验收合入。
6. 必需检查通过后逐条确认人工验收标准，点击「验收这个版本」。验收后仍可暂存交付。新增实施轮次、修改范围、代码被外部改动或检查配置变化后，需要重新封存验证和验收。
7. 点击「准备合入这个交付」。系统针对最新主线建立独立集成候选。存在冲突或回归失败时，可在原对话处理候选，也可在显示的候选目录手动处理后重新验证。源交付和主线在此阶段保留。
8. 审阅候选相对源交付的组合变化和检查证据，明确确认最终合入。主线与源引用在同一个 Git 引用事务中复核，主线已变化时过期结果不能合入。A、B 的实施、验收和合入顺序可分别决定。
9. 在「演进与回放」按需求或事件筛选历史。可查看当时范围、交付差异、验收、候选、检查日志及保存的对话；查看历史不会启动 Agent 或重放命令。主线节点列出该版本实际包含的需求。
10. 「验证当前主线」独立运行回归；最新主线失败不会抹掉历史已合入事实。撤销某次合入会创建新的需求与撤销改动，再走验证、验收、合入流程，保留后续历史。

归档只改变可见性。清理工作区是单独操作，仅允许代码已合入且无未封存改动的工作区；先停止空闲进程和终端，再让 Git 执行非强制清理。清理后使用需求历史回放对话。交付、候选、日志和 Git 快照引用默认保留，不自动设置过期时间。

## 验收覆盖与限制

| 范围 | 已加入的验证 |
| --- | --- |
| 独立工作区、A/B 乱序合入、非默认分支 | 真实 Git 集成测试与浏览器完整流程 |
| 文本冲突、无文本冲突的行为回归、候选修复 | 隔离候选、主线不变、重新验证、源交付保留 |
| 主线与源引用变化、候选过期 | 最终引用事务与目标写入竞态测试，工作区身份复核 |
| 版本化验收、必需与非必需检查、代码被检查修改 | 真实命令证据、配置修订、失败与缺失验证的阻断 |
| 并发、排序、依赖、共享检查资源 | 项目名额、真实前置祖先关系、循环拒绝、独占资源和全局单进程运行 |
| 重启、重复请求、迁移、归档清理 | 合入中断对账、持久操作身份、旧数据备份、未合入保护 |
| 主线回归、撤销与历史回放 | 最新失败与历史事实独立、保留后续提交、清理后的只读对话 |
| 页面与原功能 | Chromium 桌面/390px 窄屏、新旧任务和对话、审批、导出等原有非视觉 E2E |

自动测试使用真实 Git 与检查进程，以及可控的 Agent RPC fixture；没有使用真实模型完成需求来代替这些断言。本环境为 Linux，macOS/Windows 原生 Git、终端和桌面流程仍需在对应系统验收。桌面 TypeScript 构建与跨平台路径实现通过检查，不能替代原生运行测试。

工作区不自动复制依赖、密钥或本机配置。共享数据库、端口等环境须用检查的独占资源名与命令约束；系统不会自动改写项目测试工具的端口配置。检查日志保存有长度上限并标记截断，常见凭据及已知环境凭据会脱敏；代码和产物按用户确认的 Git 快照保留。现阶段不自动推送、发布或操作远程 PR。

### 本轮产品交互更新

“对话”和“工作”分别保留各自最近位置。需求工作区中的“专注对话／专注审阅”只改变布局，仍属于同一需求；双栏可拖动分隔条，也可聚焦分隔条后用左右方向键调整、Home 恢复默认宽度。

新需求可以先只读讨论，再完善范围与验收标准后实施。自由对话中的“整理为需求”可选择项目和来源片段，保存讨论依据与可用图片，进入需求草稿；选定讨论会作为后续轮次的背景，以当前确认的目标和验收标准优先。来源代码、未提交修改及原检查结果不自动纳入交付。

“待我处理”列出当前需要决策的事项，全局“工作动态”提供跨模式入口。其他需求的审批与提问不会直接打断当前需求。排队原因、验证占用和已归档前置需求在对应位置显示。

封存交付时可以填写行为说明、未完成项和产物文件路径。产物须已纳入交付的 Git 提交，预览从该提交读取，单项最大 2 MiB。人工验收可逐条记录观察并引用实际检查或产物；返工可以仅记录，也可以确认反馈后直接继续实施。

“演进与回放”增加主线版本列表与版本比较。历史合入和当前范围进展分别显示；撤销仍通过新需求实施，保留原主线历史。

需求对话的“从最近对话隐藏”只整理列表，工作台中的“归档需求”才改变需求生命周期。文字及图片草稿在同一浏览器会话内恢复，图片实际发送前会检查可用性；已提交到需求轮次的附件在本地保存以支持排队与重试。

## 需求 PRD 与模块设计文档

需求实施前原来只检查目标和验收标准是否非空；现在新需求先确认范围、保存并确认具体 PRD 版本，再进入实施。执行和交付同时绑定范围与 PRD；实施后的设计调整会使旧交付失效，最终验收固化 PRD。历史需求可显式启用，既有证据不被补写为已确认。

项目新增模块文档：先建立模块基线，需求 PRD 关联模块并提出完成后的完整设计，验收时发布模块新版本。模块当前设计、进行中的提案、历史版本与来源子 PRD 双向关联；对应代码是否已合入单独显示。并行需求使用模块依据版本检查，防止覆盖其他需求已发布的设计。

Agent 在独立工作区同步修改 `docs/qingzhou/requirements/<需求 ID>.json`，轮次结束后自动读回为新 PRD 草稿。确认新版本后继续实施；封存检查工作区与确认版本，并核对提交中的设计 JSON，确保设计进入同一交付。面板支持手动同步、草稿恢复、采用 Agent 回复、Markdown 导出和创建关联子需求。
