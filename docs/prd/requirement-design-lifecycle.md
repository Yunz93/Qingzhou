# 需求设计流程与模块文档 PRD

状态：已实现，待用户验收。适用于启用项目编排后的新需求；历史需求可显式启用。

## 用户目标

一个需求在同一对话内完成沟通、范围确认、PRD 确认、实施、设计迭代、回归和最终确认。最终确认时保留真实交付依据、固化本需求的 PRD。后续需求引用历史 PRD，并继续更新同一模块的设计文档。

## 两类文档的职责

| 文档 | 回答的问题 | 更新方式 |
| --- | --- | --- |
| 需求 PRD | 这次为什么改、改什么、按哪个方案实现和验收？ | 每次保存新增版本；确认精确版本后实施；最终验收固化该版本 |
| 模块文档 | 这个模块目前确认的完整设计是什么，来自哪些需求？ | 模块建立基线；需求 PRD 提出变更后的完整设计；最终验收后形成模块新版本 |

一份需求 PRD 可关联最多 8 个模块，一个模块可关联多个需求 PRD。关联保存模块依据版本、变更后的完整设计、来源 PRD 和交付 ID，能够双向追溯。

“当前确认设计”和“代码已合入”分别呈现。允许 A 已验收固化但未合入，B 继续独立推进；模块文档标明对应交付尚未合入。实际 Git 依赖仍通过前置需求与集成检查表达，文档关联不会隐式建立代码依赖或替代组合验证。

## 需求实施流程

1. 创建需求后进入沟通准备，允许只读讨论。保存需求不直接启动实施。
2. 在范围中记录目标、边界与可判断的验收标准，用户确认当前范围快照。
3. 与 Agent 讨论 PRD，支持将草稿带入只读对话、采用最新回复为草稿或直接编辑。填写方案与模块影响，保存 PRD v1。
4. 用户确认 PRD v1；单项启动、批量启动和反馈续做都由服务端检查确认状态。仅靠提示词不能越过门禁。
5. 执行记录绑定范围 ID 和 PRD ID。实施完成后仍可继续调整设计；保存新 PRD 后重新确认并开始对应实施轮次。旧交付不能用于验收新 PRD。
6. 封存代码与设计，运行真实项目检查，再逐条人工审阅。最终“验收并固化 PRD”同时记录验收、固化 PRD、发布关联模块新版本。这个动作不自动合入代码。
7. 后续变更通过“基于此 PRD 创建子需求”或“为此模块创建子需求”开始，保留来源 PRD 和模块关系，使用模块的最新设计作为提案基线。固化正文不能覆写。

## PRD 与实现同步

确认后的 PRD 在首次实施前写入独立工作区的 `docs/qingzhou/requirements/<需求 ID>.json`，包含 `schemaVersion`、`prdId`、`content`、`moduleChanges`。该文件随代码一起纳入交付和 Git 集成；关联模块的完整设计提案也在文件中。

Agent 调整设计时同步修改该文件的正文与模块提案，不更换依据 PRD ID。本轮结束后，服务端读取文件，将变更保存为待确认的新 PRD，保留之前的版本。用户重新确认后继续实施，工作区文件更新为新的 PRD ID。设计面板提供手动同步入口，处理外部修改或中断后的恢复。

文件无效、缺失、存在未同步修改、基于过期 PRD 或未纳入 Git 时，不能生成有效交付。封存前比较工作区文件与确认 PRD，提交后再次读取 Git 对象核对。不会把 Agent 的完成声明当成文档已同步的证据。

最终验收前检查当前浏览器是否留有未保存的 PRD 草稿；有草稿时先保存并确认，或明确放弃修改，避免固化时遗漏本地设计调整。

未保存的面板草稿保留在当前浏览器 sessionStorage；已保存版本由服务端持久化。服务器出现新版本时，未修改的编辑器自动载入；有本地修改则保留草稿，提示用户对照合并，使用版本 ID 防止覆盖。

## 并行修改同一模块

确认 PRD 和最终验收都检查模块依据版本。A、B 从模块 v1 并行提出变更，B 先验收发布 v2，A 不能覆盖它：用户需对照 v2 合并设计，保存并确认 A 的新 PRD，再实施、封存和验收。

多模块发布先检查全部模块，全部有效后统一写入模块版本、PRD 固化和验收记录。任一模块过期都不部分发布。PRD 迭代不改写旧版本，模块迭代也不改写历史快照。

## 界面与回放

- 需求工作区增加“设计与 PRD”，呈现范围确认、PRD 编辑/确认、工作区同步、版本历史和固化后的子需求入口。
- “将草稿带入对话讨论”切换为只读讨论意图，不沿用上一轮实施意图。
- 项目“待我处理”增加需求与 PRD 确认；未确认的需求不能批量执行。
- 项目增加“模块文档”，展示当前确认设计、代码合入状态、进行中的 PRD 提案、历史模块版本和来源需求。
- 固化 PRD 与模块文档均可导出 Markdown；交付内保留可供程序核对的设计 JSON。
- 事件回放增加范围确认、PRD 修订/确认/固化、模块发布和设计同步异常，关联原有执行、检查、验收和集成事实。

## 兼容与边界

历史需求不虚构已有 PRD 的确认或固化，原交付保持原事实，可显式启用新流程。新流程适用于启用项目编排后创建的需求。

设计正文有长度限制；若完整范围、PRD、模块正文超过执行上下文上限，要求精简或拆分，不静默截断设计。PRD 版本确认、人工验收与合入仍是用户决定。系统核对版本和文件一致性；实现是否满足产品设计仍需真实检查与人工验收。

模块文档的发布依据是最终验收。尚在设计或实施中的变更以提案展示，不直接覆盖当前确认设计。后续撤销需求也应关联受影响模块，明确反向设计，经过相同确认和交付流程。
